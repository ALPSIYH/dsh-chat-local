# dsh-chat-local

面向 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的本地多 Agent 群聊插件。

**Agent 是持续的身份，DSH Session 是它执行工作的会话。** 同一 Agent 可通过不同参与关系进入多个群组与对话，并携带自己的性格、工作偏好和实际见过的经历。对话里的职责、当前任务和原生会话配置分别管理；复用一个 Session 不会把另一身份的私人判断交给后来者。

会话历史、文件授权、原生权限预设与部署级模型默认由 DSH 管理。群聊新建成员时会保存一份已提交的工作目录、模型和可选 Agent 预设，用于创建或接续原生会话；接续已有会话的成员引用该会话。群聊中修改的原生权限与模型会留在真实 Session 上，离开群聊后仍生效。

```
Agent               稳定身份、独立人格 Markdown、本人亲历记忆
 └── 参与关系         在群组或对话中的职责，以及执行用的 DSH Session
群组                 协作团队、成员与默认配置
 └── 对话             共享消息、章程、台账、材料与运行记录
      └── 执行回合     一次有边界的成员唤醒与回复
```

## 它解决什么问题

让多个 Agent 协作，通常要么把同一份配置复制多遍，要么让它们共用一个上下文互相干扰，而且事后无法说清「谁在什么时候为什么改了这条结论」。

这个插件换一个做法：群聊只是**编排层**，不接管执行。成员通过真实的 DSH Session 执行，所以你在群聊里做的权限和模型设置，离开群聊后依然生效；反过来，DSH 自身的沙箱和审批也始终有效。

## 环境要求

| 依赖 | 说明 |
| --- | --- |
| DeepSeek Harness | `0.1.5-rc.2`（适配其槽位系统；其他版本需自行验证） |
| [`dsh-bridge`](https://github.com/baixianger/dsh-bridge) | 必需。负责本机 Session 唤醒与消息投递 |
| Node.js | 与所运行的 DSH 相同 |

不需要远程服务，不依赖 `dsh-weave`。

插件版本号以 `package.json` 的 `version` 为唯一来源，`/api/dsh-chat-local/health` 直接读取它，不另行维护副本。DSH 兼容范围声明在 `dsh.engines.dsh`，支持该字段的安装器（如 dshmarket）会据此提示版本不匹配；两者都有回归测试锁定，避免升级时漂移。

## 安装

```bash
# 从 GitHub 安装到 web profile
dsh plugin --profile web add github:ALPSIYH/dsh-chat-local

# 本地开发时用 link: 方式
dsh plugin --profile web add link:/path/to/dsh-chat-local
```

安装后重启 `dsh web`，在 DSH 侧栏底部点击「群聊」进入工作区。

> 插件通过 `cordis.patch.yml` 注册自身，不修改 DSH 源码。它占用 DSH 的原生槽位（`shell.overlay` 覆盖层），「返回 DSH」一步恢复原界面。

## 快速开始

1. **建群组** — 输入群组名称，加入已有 Agent 或新建 Agent。纯保存不创建原生 Session，也不会唤醒任何模型。
2. **开对话** — 写下议题即可开始。每个对话拥有独立的消息、台账和成员绑定；首条人类消息会生成可编辑的议题标题。
3. **让成员干活** — 默认「自动协作」：一条普通消息会按成员顺序依次征询。也可以切换为仅 `@`定向，或在消息里点名 `@别名` 精确路由。
4. **看台账** — 顶栏「台账」把任务、决定、证据和分歧从聊天里抽成可追踪条目，带负责人、验收标准和来源消息。

成员之间可以 `@` 彼此，形成 A→B→A 的因果链；普通 assistant 回复由 Session 事件自动回收进群聊，不要求 Agent 额外调用发送工具。

## 主要能力

### 协作路由

- 普通人类消息默认按成员顺序依次征询，单轮内不会并发争抢同一上下文。
- Agent 回复中的精确 `@别名` 优先路由给被点名者；人类直接输入 `@别名` 同样识别。
- 每个 Agent 在一条链内默认最多发言 3 次，整条链最多 10 次自动回复，避免无限互聊。
- 新消息令旧轮次过期，迟到回复不会污染新上下文。运行中的回合可从顶栏立即停止。
- `(pass)` 表示本轮无新增内容；未继续 `@` 时不追加点名轮次。
- 投递状态分别展示排队、已发送、已送达、思考中、已回复、跳过、失败和过期。失败投递可只重试失败的参与者，沿用原消息与因果链。
- 人类消息可追加「纠正」：原文不被改写，纠正关联原消息，并只通知曾收到原消息的参与者。

### 协作闭环台账

`chat_work` 提供 record / amend / acknowledge / progress / submit / review / comment 七种语义操作，贯穿一条明确的责任链：

| 环节 | 含义 |
| --- | --- |
| 分派 ≠ 收悉 | 负责人只能由本人确认；无负责人的任务可由成员认领 |
| 交付 ≠ 验收 | 提交必须标明材料或结果版本，进入 `in_review`；指定了独立验收人才由其确认，否则等待用户。负责人不能换一个 Session 代替独立 Agent 自验收 |
| 建议 ≠ 授权 | Agent 登记的决定初始为 `proposed`，不能自行变成 `decided`；分歧和证据不能由 Agent 单方关闭 |

除登记外，每个操作都要带事项 id、当前 revision、唯一操作 id，以及 1–8 条本房间的真实来源消息。身份取自执行工具的 DSH Session，且只允许该房间的有效群聊回合写入。幂等键相同且内容相同返回原结果，同键不同内容拒绝。

变更范围或负责人会清除旧的收悉/交付/验收并重新开放；归档不表示验收。每房间最多 1000 项台账、每项最多 1000 条历史事件，容量不足时拒绝新增而非截断历史。

### 持续身份与人格

Agent 名册中的「人格」打开独立 Markdown 编辑器，描述这位 Agent 跨工作保持的性格、价值取向、沟通偏好与工作习惯。人格不替代房间职责、章程或当前指令，也不会由一次评价或关系计数自动改写。

每位 Agent 的文件保存在状态目录的 `agents/<SHA-256(agentId)>/PERSONA.md`，上限 **8000 个 UTF-16 码元**（JavaScript `String.length`）。未填写的模板不会作为已配置人格注入。保存使用内容哈希 `expectedHash` 检查版本；发生冲突时保留草稿并要求比较，旧版本按内容哈希留在同目录的 `history/`。保存后后续任务读取新版本，已取样的回合保持原样。

`chat_identity` 读取执行者本人的稳定身份与人格。工具不能指定任意 Agent id，也没有修改人格的工具；用户可以通过编辑器或本地管理 API 编辑。没有房间上下文时，只有 Session 明确对应唯一 Agent 身份才提供个人上下文；存在历史复用歧义时需要指定本人所在房间，不猜测归属。

### 本人亲历的长期记忆

个人记忆跨越同一身份参与过的工作，保留来源和证据。它由 `memory.observed` 收据与本人的判断投影而成；**加入房间不等于看过全部历史**。

| 来源 | 何时成为个人记忆 |
| --- | --- |
| 群聊消息 | 投递确认成员收到后，记录本次提示词所含的近期消息；单独的「已发送」不算见过 |
| `chat_memory` | 工具实际返回的近期消息、章程、提案与台账，附观察收据 |
| `chat_read_document` | 工具实际返回的文档片段，保留版本哈希与行号；不推断未读取部分 |
| 本人群聊输出 | 自己已提交的消息 |
| 模型可见的工具结果 | 插件收到 `tool/result` 中实际提供给模型的文本，群聊回合按接收者绑定；不读取工具参数或隐藏元数据 |
| 原生会话 | 插件实际收到的 `user/message`、`assistant/message`、`tool/result` 文本，且该 Session 能唯一绑定到 Agent 身份；包括宿主提供的可见上下文，群聊投递期间由群聊路径记录 |
| 本人的判断 | 本人记录且仍有效的 appraisal，保留对象身份、立场、把握和证据 |

`chat_recall` 查询执行者本人的经历与判断，返回来源、证据 id、截断信息和覆盖范围。查询最长 2000 码元，`limit` 为 1–100，分别限制经历与判断条目数；每条经历返回文本最多 2000 码元。文档及原生事件的存储摘录另有上限，返回元数据会说明截断。检索使用文本匹配、相关对象与日志时间戳排序，没有向量检索或自动记忆整理。

既有日志没有观察收据的内容不会被补写成「过去已见」。插件不扫描屏幕、未观察的私信、工具隐藏元数据或推理内容，也不把图片字节转换成文字记忆。重复读回本插件的个人摘要不会被当作新的经历；个人接口不会返回其他 Agent 的私人记忆。来源不可读或完整性失败时，返回 `partial` 并列出不可用来源；没有收据也可能意味着未记录，不能据此断言从未见过。

群聊每回合取样一次人格、个人记忆与房间关系摘要。**个人记忆最多 600 码元，房间关系摘要另有 600 码元上限**，人格块另计，整条提示词不限于这 1200 码元。摘要保留来源归属，放不下的条目整条省略；成本记录包含选择、截断和省略信息。`personalMemory` 默认开启，关闭时停用个人查询/注入与原生观察收集，群聊审计收据仍保留；`appraisalDigest` 默认开启，关闭时不自动注入主观判断，显式查询仍可读取。

宿主提供 `systemPrompt` 服务时，插件还通过 `system-prompt/assemble` 为能唯一绑定身份的普通原生回合提供人格与个人记忆。群聊回合使用自己的取样提示词；旧宿主没有该服务时仍可使用群聊注入和个人查询工具。历史材料作为背景，不构成新的任务或权限授权。

### 房间运作记录与主观判断

原有 C 层的十个计数描述**对象在本房间的运作记录**；同一对象在各观察者行下的数字相同。它们不是「A 比 B 更信任 C」的私人关系，也不从聊天语气推断性格。

| 计数器 | 记录的事件 |
| --- | --- |
| `deliveriesOffered` / `deliveryFailures` / `deliverySuccesses` | 发给该成员的投递与结果 |
| `reviewsApproved` / `reviewsChangesRequested` | 该成员亲自提交的验收结论 |
| `blockedReports` / `blockedConfirmed` | 该成员报告的阻断及后续处置，按事项配对 |
| `unresolvedDisagreements` | 尚未闭环的分歧 |
| `charterProposalsSuperseded` | 该成员提出、后来被取代的章程提案 |
| `messagesAuthored` | 该成员署名的房间消息 |

`lib/relationship.js` 对日志前缀作纯函数派生，事件按 `(tick, at, id)` 排序。同一输入可重算同一结果。每回合的 `relationship.snapshot` 留存计数；提示词和治理门使用同一次取样。HTTP `relationships` 返回各对最近记录过的快照，尚无快照时为 `{}`，不会把缺失误当成已观察到的零。

A 层 appraisal 是**本人对另一成员的表态**。`chat_appraise` 需要有效、未被取代的当前群聊回合，要求立场 `trust` / `distrust` / `neutral`、0–1 的把握、本人写下的主张和证据。证据必须属于本房间，且是本人实际获知的允许材料或本人已署名的记录；仅仅知道一个事件 id 存在不足以引用，其他观察者的私人 appraisal 不能成为证据。台账或章程材料可先通过 `chat_memory` 阅读。

撤销追加新事件并保留原记录。新记录同时保留 Session 和稳定 Agent 身份；Session 换绑时不会把旧身份的判断交给新身份。旧记录缺少稳定身份时只在历史绑定无歧义的房间兼容路径可见，不推断跨房间的个人归属。主观判断不会增加 C 计数，也不会修改人格。

`chat_relationships` 只返回调用者自己的计数行和现行判断；本地管理端点 `GET /rooms/:id/relationships`、`GET /rooms/:id/appraisals`（均位于 `/api/dsh-chat-local` 下）可读取完整矩阵。**管理 API 不认证本地调用者**，私人隔离针对 Agent 工具和提示词，不对有本机文件或管理 API 访问权的进程承诺保密。

### 事件日志、提交与恢复

`rooms.json` 是当前读模型。`events/<roomId>.jsonl` 是按房间记录的 SHA-256 事件链，`.jsonl.head` 保存头部锚点。日志涵盖消息、投递、回合安排与原样提示词、成员、台账、关系快照、观察收据、appraisal、治理门及实验事件。一般只追加；快照恢复会替换该房间整份日志。删除房间不自动删除日志。

写入器默认分配房间内严格递增的 `at`；突发追加可让它领先墙钟。显式传入的有限 `at` 会原样保留，因此不承诺任意导入或显式时间戳日志都单调。`at` 用于顺序与出处，评测时长使用 `tick`。

`RoomJournal` 统一处理状态落盘、审计发布、恢复与一致读取。依赖房间状态的队列事件只在对应状态保存成功后发布；保存失败时保留队列待后续成功提交。要求当前权限的追加（包括 appraisal 与观察收据）在同一边界重验房间对象和授权，已完成的恢复会拒绝旧回合继续写入。普通审计追加仍是尽力记录，失败计入 `/health` 的 `audit`，不保证每次协作都有完整日志。

`EventLog.read` 与同一实例的追加、替换按房间排队，读取日志与锚点期间不会被该实例的写入穿插。`readRoomMemory` 和快照导出等到状态与审计完成，再读取稳定提交版本，避免把未落盘的房间对象与旧日志配对。**这些保证限于一个服务实例**：不提供跨进程锁，也不保证 `rooms.json`、日志与锚点在崩溃时共同原子提交。

- 校验：`node scripts/verify-event-log.mjs <roomId> [--state <rooms.json>]`，只读校验磁盘链与锚点，失败以非零码退出。对在线状态目录跨进程读取没有快照锁，复核时宜使用停写后的副本。
- 导出：`GET /api/dsh-chat-local/rooms/:id/snapshot?configHash=…`，包含已提交房间、事件与内容哈希；这是房间 run 快照，不含其他房间、人格文件或原生 Session 历史。
- 恢复：`POST /api/dsh-chat-local/rooms/:id/restore-from-snapshot`，请求 `{"snapshot": …, "confirm": true}`。先校验快照和事件链、备份状态为 `.pre-restore.bak`，再作废旧回合并串行恢复。恢复本来就会丢弃快照之后的房间事件，不能把它当成保留全部新数据的合并。

完整模块边界和数据流见 [Agent 记忆架构](docs/agent-memory-architecture.md)。

### 实验脚手架

这是插件记忆条件的记录与**描述性分析工具**。它不证明随机分派、独立样本或因果效果；满足样本门槛也不会输出因果结论。

`POST /api/dsh-chat-local/rooms/:id/run-manifest` 接受 `{"arm":"persistent","appliedBy":"human"}`，`arm` 也可为 `reset_per_episode`。manifest 记录运行时报告的模型、状态版本、配置内容与 `configHash`；模型未知记为 `null`，不接受调用方自报模型。每次投递前还读取该接收者的 `modelAtDelivery`，在 `injection.cost` 标记 `modelObservation: "before-delivery"`；这只证明投递前的配置快照，不证明整个模型执行期间恒定。接口不注册为 Agent 工具，并在本房间有群聊回合运行时拒绝变更。`appliedBy` 是调用声明，不是本地身份认证。

| 条件 | 行为 |
| --- | --- |
| `persistent` | 保持插件记忆投影的累积窗口；无 manifest 时也是此行为 |
| `reset_per_episode` | 每个根消息 episode 开头追加一次版本化的全记忆 `clear`；同一 run 中重试该根消息不重复清除 |

reset 关闭房间 C/A 的旧窗口，并在该条件的个人查询与注入中限定本房间、该 episode 后实际观察的材料。**它只重置插件记忆投影**，不删除审计日志、不清空人格、不清空 DSH 原生上下文，也不移除共享对话历史。成员可从当前提示词或再次读取旧消息重新获得内容，因此 reset 不是「没有记忆的人」或独立对照。

人工干预使用 `POST /api/dsh-chat-local/rooms/:id/relationship-intervention`，需要 `appliedBy: "human"`、`mechanism` 和 `action: "clear"|"set"|"seed"`，同样只在房间空闲时受理。默认 `memoryScope: "counters"` 只改 C 的计数窗口；`memoryScope: "all"` 仅允许整房间 `clear`（不指定 `observerId` 或 `targetId`），同时重置 C/A 与该房间个人观察窗口。干预保留之前的 counters 与完整事件。按对象的计数干预可给 `targetId`；`observerId` 只记录，不会把对象计数变为某一观察者的私有值。

`configHash` 包括房间指令与成员标签/职责、治理门、记忆开关、人格哈希、渲染与派生版本，以及明确列出的后端本地模块源码闭包。注释和排版也改变指纹，可能保守地拆分等价组；第三方依赖、宿主全部提示词、模型隐藏状态与随机性不在此指纹内。历史内容不是配置。每次群聊注入还记录实际配置哈希、人格版本、记忆可用性与截断信息。评测比较 `modelAtDelivery` 与 manifest 对应成员的 provider/model/推理等级；已知配置漂移、观察结构无效或已知模型后来不可读取，会排除整个 run。配置哈希漂移或已声明的记忆不可用也会被拒绝；缺少逐注入检查字段的旧格式标记为 `legacy-unverified`。指纹相同只说明记录字段相同，不证明实验条件完整可比。

`turn.prompt` 留存原样提示词，`injection.cost` 分别记录房间摘要、个人摘要、人格的字符数及估算 token 成本；token 数不是模型账单。记录发生在投递前，因此成本记录存在不等于提示词已被接收。

```bash
node scripts/relationship-eval.mjs --state /path/to/rooms.json --observation
node scripts/relationship-eval.mjs --state /path/to/rooms.json --json
```

评测按 manifest 切分房间日志，依 `(arm, configHash, initialStateVersion, models)` 分组，`models` 中已记录的 `reasoningEffort` 也参与分组，缺失/null 视为未记录。provider/model 未知的 run 不与其他 run 合并。默认每组需要至少 **10 个有效且有已到达成员交互的 run 片段**才展示跨 run 统计；每项指标还要有足够的有效观测，缺少验收、接手或分歧的分母记为缺失，不能填零。报告给出均值、有效样本数、缺失数和样本离散程度，单值方差为空。十次空 run 或失败投递不能满足门槛，同一房间的多个 run 仍可能共享历史。

`--observation` 显式允许小样本描述统计，`--min-runs` 只能提高默认门槛。所有模式始终标记 `descriptive-only`、`independence: "unverified"`；退出码 0 表示报告成功，3 表示未达到默认报告门槛，2 表示无有效 run，1 表示参数/读取错误或报告排除了无效数据（无有效 run、门槛不足优先返回其对应码）。链损坏、异常测量和配置漂移会被报告；房间归属不符的事件不纳入该房间 run。不把脚本成功当成研究结论。

### 章程自更新

房间的目标与协作章程可由 Agent 提议、全员确认后自动生效，不需要用户手动抄录：

- `chat_memory` — 读取现行章程、近期版本、提案、最近 24 条公开消息与台账。不读取任何成员的私聊上下文。
- `chat_charter_propose` — 提交完整的新章程文本，须带现行 `baseRevision`、理由和 1–8 条讨论消息 ID。
- `chat_charter_review` — 执行 Session 只能代表自己确认或提出异议。**沉默、模型普通表态或聊天里的「同意」都不是工具确认。**

全体现有成员确认后写入新版本并在时间线公告；出现异议则保留旧章程，在轮次预算内让提案人处理。审阅与返修共用原有的每人/总回复上限，不开启无限后台轮次。

### 权限模型

每个房间带递增的策略版本，每条消息记录其提交时的策略版本与动作模式：

| 模式 | 行为 |
| --- | --- |
| `discuss_only` | 只读讨论/审计。群聊额外拦截命令、文件修改和未知副作用工具 |
| `read_only_audit` | 只读审计，语义同上，用于明确的审计场景 |
| `inherit_dsh` | 不修改原生配置，移除群聊额外拦截，由各会话当前的沙箱与审批控制 |
| `workspace_write` | 把现有成员同步为 DSH 原生 `workspace-write / ask` |
| `full_access` | 同步为 `danger-full-access / never` 并移除群聊额外拦截 |

后两项**真的调用 DSH 原生权限预设**设置成员的真实 Session，而不是只改台账或提示词——这些设置在离开群聊后仍然生效。需要用户明确勾选影响提示才会应用，应用后不会自动启动任务。

变更必须由用户在权限界面明确执行；插件层面没有任何群聊工具、章程提案或台账决定能让成员改变房间策略——`chat_*` 工具没有写策略的路径，章程提案只写章程，台账决定只写台账。房间策略端点（`/api/dsh-chat-local/rooms/:id/policy`）是**面向用户的本地端点**：它挂在回环地址上，与插件其它会改动状态的端点一样，对本地调用者不做认证，因此它挡的是浏览器跨站请求，而不是本机上已经能执行命令的进程或成员会话。需要真正的成员隔离时，须由 DSH 原生沙箱与审批来约束这些会话。批量变更前会检查所有成员是否空闲。原生服务缺失或预设不匹配时给出具体错误，不虚报成功。

**行动治理门（默认关闭）。** 房间策略带一个 `gate` 字段，缺省即不存在（等同关闭），只有显式为 `true` 时治理门才生效。它约束的是**成员执行工具**，而且**只收紧、从不放宽**：开启后不会放过任何关闭时会被拒绝的调用，受限模式（`discuss_only` / `read_only_audit`）对只读工具、群聊状态文件与内网地址的既有判定完全不受它影响。判定只发生在群聊回合处于执行类模式（`inherit_dsh` / `workspace_write` / `full_access`）时。

判定读的是**行动成员自己**的记录，即以该成员为对象的那一对计数：一次工具执行不指名对手方，所以「对象」只能是他本人。规则见下表，按顺序判定，先满足的先成立：

| 判定 | 条件 | 结果 |
| --- | --- | --- |
| 需要独立验收人 | 动作是一次评审（`chat_work` 的 `review`、`chat_charter_review`，以及映射表里没有列出的工具——它可能是一次评审），且记在他名下的分歧仍未闭环 | 拒绝执行并说明 |
| 需要用户确认 | 动作属高影响，且发给他的投递失败过、从未成功送达 | 拒绝执行并说明 |
| 不允许 | 工具名缺失，无法归类其影响 | 拒绝执行并说明 |
| 允许 | 其余情况 | 照常执行 |

两条规则同时成立时由「需要独立验收人」决定：用户确认不能替代一次本不该由他做的评审。

工具名到风险类别与动作类别的映射来自 `lib/gate.js` 里唯一的映射表：执行 shell 或代码、写文件、移动或删除文件、发布交付物、控制其他会话或进程、改动运行中的 Host、以及**生成本房间交付物时调用外部服务**（`codex_connect_image_generate`）算高影响；读取、检索、以及房间内的消息与台账操作算低影响——按名称取回外部内容的读取（`web_search`、`web_fetch`、`fetch`）也在低影响一侧，它们只读回内容，不改变任何东西。`chat_appraise` **显式登记**在低影响、动作为房间内事务（`work`）那一侧：它只往本房间的日志里写一条 `appraisal`，不改任何用户文件、权限或其他 Session，对别人做过什么也不下任何结论，所以它不是评审动作；漏登记会让它落入兜底档（高影响 + 可能是一次评审），从而对一个名下有未闭环分歧的成员拒绝他自己写下的表态。

映射表里**没有列出**的工具在判定时**同时**按高影响、以及按「这**可能**是一次评审」来读（与受限回合的只读白名单同一立场：新工具要被显式登记）。这张表是判定工具类别的唯一处所，而「这是一次不该自评的评审」正是一个未登记的工具可能具有的效果，所以漏登记只会更严，不会更松：一个能写验收结论的新工具若漏登记，对那个分歧仍未闭环的成员同样会被「需要独立验收人」拒绝，而不是被放行。

确认规则只作用于高影响的那条判定：高影响动作在「房间无法可靠触达他」时要求确认，也就是 `deliveryFailures > 0` 且 `deliverySuccesses === 0`；一次成功送达就会改变这条记录。

治理门**不提供交互式审批**：工具守卫只能拒绝并说明，被拒的成员能看到自己遇上的是「需要用户确认」、「需要独立验收人」还是「不允许」。命中时房间追加一条 `action_gate` 事件，记下工具名、判定、风险类别，以及判定依据的那一对计数器与它取自哪个回合的关系快照；该事件不参与关系计数器的派生。

两条规则都读「那一对计数」这**一个**采样，而它的来源是房间已经记录下来的日志：判定用的是该回合的 `relationship.snapshot` 所用的那次派生，也就是该成员在提示词里读到的同一组数字。**快照缺失或不可读时，两条规则都不成立，动作放行。** 这是有意的 fail-open，也是整个承诺生效的**前提**：门只在审计层可用时才真正收紧。规则是阈值 `> 0`，而「没有证据」与「计数全为零」在观测上不可区分，因此不会反过来被当成对某个成员不利的推定；新房间在第一次快照之前本来就没有样本，若在这里 fail-closed，第一个高影响动作就会被拒，门在这些房间里等于不可用。日志读不出来时该回合不发快照、也不注入摘要，行为与「还没有任何快照」一致。

关闭时与没有治理门时行为一致：工具的执行结果与拒绝文案、`turn.prompt` 文本都不改变，也不会产生任何 `action_gate` 事件；未开启过的房间，其策略里也不会出现 `gate` 字段。**`injection.cost` 不属于这项对比**：它是每次唤醒成员都会追加的注入成本记录，与治理门无关，开关前后都在——事件序列里多出的是这条仪表记录，不是门的产物。开关通过房间策略接口生效（`POST /api/dsh-chat-local/rooms/:id/policy` 的 `gate` 字段，与 `defaultActionMode` 一同提交，沿用该接口的策略版本）。这个接口沿用既有的执行权限确认：调用里**只要具名一个执行模式**就要求 `confirmRisk`，缺少它整条调用被拒绝。这与权限是否真的变化无关，所以**把当前生效的执行模式原样重送**（例如 `inherit_dsh` → `inherit_dsh`）、以及重新应用 `full_access` / `workspace_write` 的原生预设（后者每次都真的重写成员的原生会话），同样会被拒绝。唯一豁免的是**只改 `gate`、模式与预设都不动**的那次调用：它不具名任何执行模式的变更，也不改变任何权限。只读模式（`discuss_only` / `read_only_audit`）在原来就不需要确认，现在也不要求。

### 材料读取

`chat_read_document` 可在群聊回合内安全地分段抽取 DOCX 或文本，无需 shell：

- 读取范围限于参与者工作目录，或用户在群里**明确共享的单个路径**；不开放邻近文件或整个目录。
- 文本上限 1 MB，DOCX 压缩文件上限 20 MB。按受限 ZIP/XML 解析，不运行宏、不跟随外部链接、不修改原文件。
- 返回正文、表格、脚注、尾注、批注、页眉页脚的 XML 定位码与版本哈希。这是结构化文本抽取，**不等于**页面排版或图像审查。

历史记录只作为带 SHA-256 的只读来源引用：插件区分 Artifact（逻辑文件）、Version（内容哈希版本）和 Replica（某会话工作目录中的副本），不复制或改写原文。

### 界面

- Agent 名册提供独立人格 Markdown 编辑器，保留未保存草稿并显示版本冲突。
- 沿用 DSH 的主题颜色、字号与线性图标，不使用 Emoji。
- 桌面默认展开房间栏；680px 以下改为房间抽屉，1120px 以下详情使用遮罩抽屉。
- 消息按日期分组，「回应」可跳转并短暂高亮原消息。向上阅读历史时新消息不会抢走滚动位置，而是显示「新消息」按钮。
- 草稿按房间保存并在返回后恢复；异步发送结果会校验房间 ID，不会把 A 房消息写进正在查看的 B 房。
- Esc 只逐层关闭选择器、确认框、检查器或新建表单，不会退出群聊。
- 删除房间是**可恢复的软删除**：房间移入「已删除」，消息、成员关系和真实 DSH Session 全部保留。「移出」只移除房间成员关系，不删除 Session。

## 本地数据

房间状态保存在 `~/.dsh/dsh-chat-local/rooms.json`，目录权限 `0700`、文件权限 `0600`，当前状态版本 **v16**。

- 读取到不支持的未来版本或无效顶层结构时停止加载，不以空状态覆盖原文件。
- 旧版程序不能读取 v16。升级前请备份；备份只保存升级时点，直接覆盖旧备份会丢失之后新增的数据，本版没有无损降级工具。
- 软删除不清除房间历史。旧章程、台账、消息、原生会话绑定和分享范围都会保留，不伪造过去的修订或验收记录。
- 导出按钮把房间读模型写成 JSON（含状态内的章程/台账历史与 SHA-256，不含独立事件日志）或 Markdown（完整对话与当前台账），写入 `~/.dsh/dsh-chat-local/exports/`，每次生成唯一文件名、不覆盖旧备份。导出不会另行读取私聊、密钥或引用文件。
- `events/` 保存房间日志及按 Agent 隔离的原生观察日志；`agents/` 保存人格 Markdown 和旧版本。备份长期记忆时应连同状态目录保存，单份房间快照不包含这些全部资料。
- 事件日志包含原样群聊提示词与已观察内容，可能包含人格和读取的文档摘录。它不是脱敏导出，应按实际内容管理访问与保留。

## 开发

```bash
npm run build    # 把共享协议嵌入浏览器入口
npm run check    # 生成代码一致性 + 语法检查 + 全部回归测试
npm test         # 仅跑回归测试
```

`lib/text-protocol.js` 与 `lib/work-protocol.js` 是前后端共享的协议定义，由 `lib/client.js` 中的生成区块内嵌。**修改协议后必须重新运行 `npm run build`**，否则 `npm run check` 会因生成代码过期而失败。

提交前请确保 `npm run check` 全绿。当前测试覆盖房间存储、协作协议、章程与台账流程、权限拦截和 UI 组件。

`scripts/ui-fixture.mjs` 可在没有真实房间的情况下预览界面：它起一个 `127.0.0.1:3081` 的隔离服务，写入一套示例数据，并拦掉原生 Session、模型执行与真实文件访问。它借用宿主 DSH 附带的 React，因此需要 `DSH_MODULES_DIR` 指向 DSH 包内的 `node_modules`；当前 DSH 版本不再以独立包的形式附带 React，所以这个开发预览脚本在默认安装上**用不了**，会以明确错误退出。这是该脚本自身的限制，插件的安装与功能不受影响。

## 已知边界

- 这是 DSH 的**本地插件**，不是 DSH 的 fork。它使用 DSH 已有的槽位、Session、模型目录和工作目录能力。升级 DSH 后应重新运行测试并复核界面——DSH 的槽位系统在 0.1.5 有过一次重构，插件对此有硬依赖。
- 房间事件保存在单机 JSON 中，不是多设备实时协作的文档。
- **事件日志是状态目录里第二份持续增长的数据集。** `events/` 下的每个房间日志只追加，不轮转、不压缩、不自动清理，软删除或彻底移除房间都不会删除它的日志；它持续保存消息、投递、原样提示词和观察材料，文档与工具输出会增加存储量。容量、备份与保留策略由用户自行决定，本版不提供保留期、轮转或裁剪工具。
- **哈希链是篡改痕迹，不是身份认证。** 有权同时改写日志与锚点的人可以重算链，也能伪造或复制数据。来源检查与样本门槛不能证明记录真实或样本独立。
- 单实例的提交排序不等于跨进程事务；状态、日志与锚点仍可能在进程崩溃时分离。日志路径检查与打开之间仍有 TOCTOU 窗口，不支持多个写入器共用同一状态目录。
- 个人记忆目前按完整相关历史扫描并投影，读取工作量随历史增长；没有索引、向量检索、自动巩固、遗忘或容量治理。日志与人格旧版本没有自动保留期。
- Agent 工具只返回本人的私有判断与经历，但本地管理 API 不认证调用者，状态文件也不加密；DSH 原生沙箱和审批仍负责约束本机进程与会话访问。
- 停滞监控只对用户明确开启监控的台账任务生效，按分钟配置，不含工作日历、免打扰时段或跨设备通知。
- 跨房间提供的是同一身份的亲历记忆，不自动向全体成员传播私人记忆，也不读取未观察的私信侧信道。
- 外部历史记录只作为只读来源引用，不会自动把原群聊或私信导入新的活动时间线。
- 文件检查器提供文本预览与 DOCX 文本抽取，不含完整语法高亮、diff 或 Word 页面排版渲染。模型不得据文本抽取宣称完成了视觉审查。
