# 工作契約、成果版本與處理請求

v0.19 的群聊目標是讓具有持續身分的成員完成可查驗的工作。發言、執行、提交和驗收分開記錄。這份文件描述已接入的入口；模型是否會恰當使用它們，需要另看[合作評估](collaboration-evaluation.md)。

## 一次工作的使用流程

1. 未指定策略的新對話預設「按工作責任分流」；重用群組範本時沿用該範本的策略。普通要求交負責人；尚未登記工作時交協調者，沒有指定則取現有成員順序的第一位。可在「工作概況」查看實際協調者與待處理請求。沒有可用接手者就保留未處理狀態。
2. 登記任務的目標、負責人、驗收標準。最終整合也用普通任務表示，勾選「最終整合工作」，選擇必要子工作。一般關聯不自動成為必要依賴。
3. 發布成果時保存固定內容；可以是檔案，也可以是短文字結果。已發布版本可從「成果 → 文件記錄 → 閱讀歷史版本」開啟，原路徑後來改寫或刪除不會改變固定內容。
4. 提交時指定成果版本，交代已满足、缺少的項目與影響。必要子工作的採用版本固定在契約中。契約未允許部分交付時，缺项不能通過驗收。
5. 指定評審核查同一份契約、输入与成果；未指定評審則由人類核查。更正、異議和未審閱文字須處置後，整合工作才能結案。驗收保存當時的訊息截止點；其後的新文字仍列待檢視，新更正／異議明示需複核，不把已驗收成果偷偷改寫為未曾通過。契約改變則須重驗。

原先的文字交付仍保留，標為「版本未固定」。系統不能補造它當時的內容或驗收證明。修改舊任務以採用新契約時，應先重新開工、確認範圍，再固定成果。

## 訊息如何分流

| 用途 | 效果 |
| --- | --- |
| 僅告知 | 保存內容，不立即喚醒或打斷正在執行的成員；保留待審閱增量 |
| 請處理 | 形成具名處理請求，附工作與依據版本 |
| 更正／異議 | 保留需處置的請求；收到、回答或略過不自動表示採納 |
| 多人徵詢 | 在同一預算内邀请成員，完成後需整合；不能無限接力 |
| 進度查詢 | 查看工作概況；需要模型解釋時使用原執行額度，不為原工作補額度 |

新策略使用收件人選擇和結構化請求。正文中的 `@姓名`、引用同事、普通進度或附和不會自動派工。舊房間未配置新策略時保持 `legacy`，仍按原規則解讀提及。

未被喚醒的人沒有因此讀到訊息。未分類文字可能包含重要資訊，所以保留為待審閱；系統不以文字相似度刪除它。負責人須讀取原文，再用 `chat_resolve_request` 記錄原因與來源；人類亦可在工作概況處置。這是已記錄的處置，不是模型理解正確的保證。

## 契約與驗收

`revision` 管理同時修改衝突；`contractHash` 標示目標、標準、責任與採用材料是否改變。普通評論可以增加 revision，但不改契約。改變工作契約需重新收悉、提交和驗收，舊記錄保留。未處置更正／異議保留原來源與原契約，另記契約變更；修改範圍或取消工作不算已回答。

- `inputRefs` 固定成果版本，或子工作的提交 revision 和契約。
- `requiredWorkIds` 列必要子工作；拒絕自我依賴和循環。
- `submission.artifactRefs` 保存 `{artifactId, versionId, contentHash}`。
- `submission.coverage` 保存 `satisfied`、`missing`、`impact`。這些是交付者的逐項陳述，仍須評審核查。
- 驗收同时指定 `expectedContractHash`、`expectedSubmissionRevision` 和 `artifactRefs`；不能批准可變的「最新檔案」。

成果 bytes 先可靠落盤，再隨 RoomJournal 保存引用。中途失敗可能留下未引用內容，但不得回報已發布；重送沿用 operationId。讀取再次校驗 hash 和大小。內容儲存的硬上限為 20 MiB；目前發布入口的文字／程式檔上限為 1,000,000 bytes，DOCX 上限為 20 MiB，工具內嵌文字另限 200,000 字元。讀取分頁，過長單段或非支援文字格式會明確拒絕。

目前支援依次開啟舊版與新版核對，不提供自動語義差異判定。沒有原始快照的舊路徑記錄不能假裝可取回。

## 額度與停止

新策略為同一執行鏈保存預算帳，在派送給宿主前預扣。略過、失敗和結果未知均計入；內部交接、重新排程和恢復不補回額度。新的人類工作要求可開始有記錄的新額度。整合與評審從總額和相關成員額度中預留份額。

這裡的執行次數是**插件向宿主派送的次數**。宿主尚未回報模型內部重試和完整 token 費用時，值為未知，不能用回覆數或零代替。預留值是可調工程初值，沒有宣稱最適用於所有工作。

「已驗收」「已交部分成果」「等待條件」「預算耗盡」「結果未知」與底層是否仍執行分開。額度不足時保留當前成果及缺項，不用一段樂觀總結抹平未完成工作。未知外部結果不盲目自動重試。

## 工具與管理入口

| 入口 | 用途 |
| --- | --- |
| `chat_work` | 既有工作台帳的登記、收悉、進度、提交、評論和驗收 |
| `chat_publish_artifact` | 以 operationId、entryId、expectedRevision 發布該工作的固定內容 |
| `chat_read_artifact` | 按固定版本分頁讀取，保存實際讀者的觀察收據 |
| `chat_collaboration` | 查工作結果、待處理請求、待審閱增量與額度 |
| `chat_resolve_request` | 以請求 revision 和本人已見來源，記錄處置 |
| `chat_recall`／`chat_memory_update` | 本人工作相關記憶、信念、學習候選與評審快照 |

Agent 身分來自執行中的 DSH Session，不能傳入另一人的身分代辦。這些工具不提升原生權限。人類管理 API 沿用本機信任邊界，詳見[維運](operations.md)。

## 升級與保存

狀態格式 v18：未指定策略的新對話預設 work；舊對話保留 legacy，群組範本沿用已選策略。群組範本只複製策略、預算及協調者配置，不複製待辦請求或已消耗額度。執行中不能切換策略。

完整備份需含 `artifact-content/`。JSON 房間匯出與 run snapshot 可攜帶已引用的固定內容，原始 bytes 合計上限 128 MiB；匯出失敗不會靜默丟掉成果。快照還原 HTTP 请求另有 192 MiB 上限，普通訊息仍限 1,000,000 bytes。`.bak` 只備份狀態檔，不是完整災難復原。新程式切回 legacy 與二進位降版不同；降版需同時核對資料相容性。
